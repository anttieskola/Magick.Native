# Building Magick.Native

This document describes the requirements and instructions to build Magick.Native.

### Requirements

- Windows:
  - Visual Studio 2026
  - Powershell (>= 3.0)
  - Git for Windows (>= 2.7.2)
  - Windows SDK (>= 10.0.10586)
  - Docker
- Linux:
  - Docker

### Building the library

Magick.Native uses the ImageMagick 7 library and that needs to be build first. The library can be build for Windows, Linux,
macOS and WASM and each of these platforms have their own build steps. This project uses GitHub actions to build the library
and the steps that are done for each platform can be found inside the following workflow:

[main.yml](.github/workflows/main.yml)

For Linux and macOS the scripts that are in the main.yml file can just be executed. For Windows the following environment
variables need to be set before executing the scripts:

- `%QuantumName%` (Allowed values Q8, Q8-OpenMP, Q16, Q16-OpenMP, Q16-HDRI, Q16-HDRI-OpenMP)
- `%PlatformName%` (Allowed values: x64, x86)

There are also some build scripts in folder `src/ImageMagick/build` that can be used to build ImageMagick.

## How a C# library is built on top of C/C++ code

Before the step-by-step instructions, this is the big picture of how Magick.NET ends up calling ImageMagick. The
pattern is the standard one for wrapping any C/C++ open source library in .NET.

### The three solutions and what each one produces

| Solution | Language | Output | Role |
|---|---|---|---|
| `src\ImageMagick\IM7.Static.x64.sln` (generated by the Configure tool, gitignored) | C / C++ | Static libraries `CORE_RL_MagickCore_.lib`, `CORE_RL_MagickWand_.lib`, one `CORE_RL_<name>_.lib` per coder and delegate | Compiles upstream ImageMagick. No .NET involvement. |
| `Magick.Native.sln` (this repository) | C compiled as C++ | One DLL: `Magick.Native-<Quantum>-<arch>.dll` | Compiles the shim in `src\Magick.Native` and links the static libraries from the first solution into the DLL. |
| `Magick.NET.sln` (separate repository, `dlemstra/Magick.NET`) | C# | NuGet packages | Contains the P/Invoke declarations that call the DLL, and the public C# API on top. |

P/Invoke is a caller-side concept: it lives only in the C# project that wants to call native code. The native side
never "does" P/Invoke. It only has to expose plain C functions with stable names, which is what `MAGICK_NATIVE_EXPORT`
and the `extern "C"` blocks in the headers of `src\Magick.Native` guarantee.

### Why ImageMagick is built as static libraries

.NET can only load a dynamic library (a DLL) at runtime. A static `.lib` is an archive of object code with no export
table, so C# cannot call into it directly. The Configure tool is therefore run with `/static`, and the resulting `.lib`
files are linked *into* `Magick.Native-<Quantum>-<arch>.dll` by `Magick.Native.sln`. ImageMagick's code physically ends
up inside that DLL, but only the shim functions marked `MAGICK_NATIVE_EXPORT` are exported. ImageMagick's own functions
such as `BlurImage` are inside the DLL as well, but private to it: C# calls `MagickImage_Blur`, which calls `BlurImage`.

This is why the DLL is around 24 MB and has no runtime dependencies beyond the Windows system DLLs: ImageMagick plus
every delegate library (libpng, libjpeg-turbo, libheif, libjxl, freetype, pango, cairo, ...) is statically linked in.
The price is one DLL per operating system, CPU architecture and compile-time option (quantum depth, HDRI, OpenMP),
which is what the large CI matrix in `main.yml` produces.

It would be possible to build ImageMagick as DLLs and P/Invoke `BlurImage` directly from C#. The project deliberately
does not, because that would mean shipping a dozen DLLs instead of one, mirroring ImageMagick's internal structs and
macros in C# and keeping them in sync with every upstream change, and reimplementing ImageMagick's `ExceptionInfo`
error handling and channel-mask handling on the managed side. The shim absorbs all of that in C, where it is natural.

### The five layers, from upstream source to NuGet package

1. **Build the C/C++ code into one self-contained binary.** `IM7.Static.x64.sln` produces the static libraries;
   `Magick.Native.sln` links them into a single DLL. Steps 1 and 2 of the Windows walkthrough below do this.
2. **Write a thin C shim with a flat C-ABI surface.** .NET can only call plain C functions: no C++ classes or
   templates, no name mangling, and struct layouts are risky. The shim in `src\Magick.Native\*.c` wraps each
   ImageMagick operation into a function with a regular signature: pointers in, pointers or primitives out, enums as
   `size_t`, and a trailing `ExceptionInfo **` for errors. `MagickImage_Blur` in `MagickImage.c` is a typical example.
   The shim never does image processing itself; it only gives C# something regular to call.
3. **Declare those functions in C# with P/Invoke.** In Magick.NET each exported C function needs a `DllImport`
   declaration naming the DLL and the entry point. Magick.NET generates these with a Roslyn source generator from
   partial method declarations in `src\Magick.NET\Native\`. That is why the C function names must follow the
   `<ManagedClass>_<Member>` convention (properties: `<Class>_<Name>_Get` / `_Set`): the generator builds the entry
   point name from the managed class and method name.
4. **Wrap the raw pointers in idiomatic C# objects.** `MagickImage` holds the native `Image *` privately, calls the
   native methods, converts results to .NET types and implements `IDisposable` so native memory is freed. Memory
   allocated by ImageMagick must be freed by ImageMagick, which is why the shim exports `MagickMemory_Relinquish`.
5. **Ship the binaries and load the right one at runtime.** This repository publishes the DLLs as versioned GitHub
   releases. Magick.NET pins a version in `src\Magick.Native\Magick.Native.version`, downloads the matching binaries
   and packs them into its NuGet packages. At startup it picks the file name from the configured quantum and the
   process architecture. The XML configuration files collected in step 3 below are embedded into the managed assembly
   and written to a temp folder before ImageMagick initialises, because ImageMagick expects its configuration on disk.

Layers 1 and 2 live in this repository; layers 3 to 5 live in Magick.NET. The two are split because the native side
changes rarely and takes long to build on every platform, while the managed side changes often and builds in seconds.
A new feature that needs a new C function therefore travels: change here, release, version bump in Magick.NET, managed
code and tests. The commit "Added channel argument to Normalize" in this repository and its counterpart in Magick.NET
are a small, complete example of that journey.

## Windows: step by step

This section walks through a complete local Windows build of one variant (`ReleaseQ16-HDRI`, `x64`). Everything below was
done on a Windows 11 machine with Visual Studio 2026 Community installed at
`C:\Program Files\Microsoft Visual Studio\18\Community` and Git for Windows at `C:\Program Files\Git`. No Docker is needed
for the Windows build.

All commands are run from a plain `cmd` prompt. You do **not** need a Developer Command Prompt: `build.cmd` calls
`tools\windows\init.visualstudio.cmd`, which locates `VsDevCmd.bat` under the Community, Professional or Enterprise
folder of Visual Studio 18 and initialises the environment itself.

### Step 0: what the repo looks like before you start

After a fresh `git clone` of this repository, `src\ImageMagick` contains only scripts and the pinned commit file:

```
src\ImageMagick\
  ImageMagick.commit        <- the ImageMagick git commit that will be checked out
  checkout-release.cmd      <- Windows wrapper around checkout.sh (downloads prebuilt dependencies)
  checkout-development.cmd  <- Windows wrapper around checkout.sh --development (clones the Dependencies repo instead)
  checkout.sh
  update.imagemagick.cmd
  update.imagemagick.sh
```

The folders `ImageMagick`, `Configure`, `Artifacts` and `Dependencies` do not exist yet. They are all listed in
`.gitignore`, so nothing created by the steps below is ever committed.

### Step 1: check out ImageMagick and download the prebuilt dependencies

```cmd
cd Z:\Magick.Native\src\ImageMagick
checkout-release.cmd x64 noOpenMP
```

Arguments:

| Argument | Values | Meaning |
|---|---|---|
| 1 | `x86`, `x64`, `arm64` | Architecture of the dependency libraries to download. Must match the architecture you build in step 2. |
| 2 | `noOpenMP`, `openMP` | Which flavour of the dependency libraries to download. Must match the last argument of step 2. |

What the script does (it finds `bash.exe` via `tools\windows\find-bash.cmd` and runs `checkout.sh` with it):

1. `git clone https://github.com/ImageMagick/ImageMagick.git` into `src\ImageMagick\ImageMagick`, then
   `git checkout <commit>` where `<commit>` is the content of `ImageMagick.commit`. If that file contains the word
   `latest`, the `main` branch head is used instead. The clone ends up in detached HEAD state; that is expected.
2. Downloads the ImageMagick "Configure" tool (`Configure.Release.x64.exe`, `.x86.exe`, `.arm64.exe` plus a
   `files.zip` with config templates) from the latest release of `ImageMagick/Configure` into `src\ImageMagick\Configure`.
3. Downloads `windows-x64-static-noOpenMP-linked-runtime.zip` (name built from the two arguments) from the ImageMagick
   repository's prebuilt dependency artifacts and extracts it into `src\ImageMagick\Artifacts`. This contains the
   already compiled static libraries for every delegate library (libpng, libjpeg-turbo, libheif, libjxl, freetype,
   pango, cairo, ...) so none of those have to be built locally.

The output is long (a few thousand lines of `inflating: ...`). It ends with:

```
  inflating: ../Artifacts/pre-build-libs.txt
  inflating: ../Artifacts/sbom.json
```

Afterwards `src\ImageMagick` looks like this:

```
src\ImageMagick\
  Artifacts\            <- prebuilt dependencies
    config\
    include\
    lib\                <- 38 static .lib files
    license\
    resource\
    pre-build-libs.txt
    sbom.json
  Configure\            <- Configure.Release.x64.exe and friends
  Dependencies\         <- empty placeholder, only populated by checkout-development.cmd
  ImageMagick\          <- the ImageMagick source checkout
  ImageMagick.commit
  checkout-*.cmd / checkout.sh
```

Step 1 only has to be repeated when `ImageMagick.commit` changes or when you switch architecture / OpenMP flavour.

### Step 2: build ImageMagick and then Magick.Native

```cmd
cd Z:\Magick.Native\build\windows
build.cmd Release Q16 x64 hdri noOpenMP
```

Arguments (all five are mandatory, the script exits with "Do not use this script directly." if one is missing):

| Argument | Values | Meaning |
|---|---|---|
| 1 | `Debug`, `Release` | MSBuild configuration prefix. `Debug` links against the debug ImageMagick libraries (`CORE_DB_*.lib`). |
| 2 | `Q8`, `Q16` | Quantum depth. |
| 3 | `x86`, `x64`, `arm64` | Target architecture. Must match step 1. |
| 4 | `hdri`, `noHdri` | HDRI on or off. `Q8` is always built with `noHdri`. |
| 5 | `openMP`, `noOpenMP` | OpenMP on or off. Must match step 1. `x86` cannot be combined with `openMP`. |

The combination of arguments 2, 4 and 5 forms the quantum name used everywhere else: `Q16` + `hdri` + `noOpenMP`
becomes `Q16-HDRI`, and the MSBuild configuration becomes `ReleaseQ16-HDRI`.

What the script does, in order:

1. Calls `tools\windows\init.visualstudio.cmd` to set up the Visual Studio 2026 environment (prints the
   "Visual Studio 2026 Developer Command Prompt v18.0" banner).
2. Changes into `src\ImageMagick\Configure` and runs
   `Configure.Release.x64.exe /noWizard /VS2026 /static /Q16 /opencl /noDpc /hdri /noOpenMP /x64 /linkRuntime`.
   This generates `src\ImageMagick\IM7.Static.x64.sln` and all `ProjectFiles` for ImageMagick (both gitignored).
3. Writes `src\ImageMagick\Directory.Build.targets`, which defines `MAGICKCORE_LIBRARY_NAME="Magick.Native-Q16-HDRI-x64.dll"`
   for the MagickCore project so that ImageMagick knows the file name of the DLL it will live in.
4. Runs `msbuild IM7.Static.x64.sln /t:Rebuild /p:Configuration=Release,Platform=x64`. This compiles MagickCore,
   MagickWand and all coders into static libraries under `src\ImageMagick\Artifacts\lib`. This is the slow part.
5. Changes to the repo root and runs `msbuild Magick.Native.sln /t:Rebuild /p:Configuration=ReleaseQ16-HDRI,Platform=x64`.
   This compiles `src\Magick.Native\*.c` and links everything into
   `src\Magick.Native\bin\ReleaseQ16-HDRI\x64\Magick.Native-Q16-HDRI-x64.dll`.

Because both MSBuild calls use `/t:Rebuild`, running `build.cmd` always rebuilds ImageMagick from scratch. For day-to-day
work on the C code in `src\Magick.Native` you only need step 5; see "Rebuilding only Magick.Native" below.

Result of a successful run (`ReleaseQ16-HDRI`, `x64`):

- `src\ImageMagick\Artifacts\lib\CORE_RL_MagickCore_.lib`, `CORE_RL_MagickWand_.lib`, `CORE_RL_Magick++_.lib` plus one
  `CORE_RL_<name>_.lib` per delegate library (ImageMagick's own static libraries; the delegate ones were already there
  from step 1).
- `src\ImageMagick\Artifacts\bin\*.exe` (`magick.exe`, `identify.exe`, `mogrify.exe`, `montage.exe`, ...) and
  `src\ImageMagick\Artifacts\bin\*.xml` (`colors.xml`, `policy.xml`, `type.xml`, ...). The exe files are a by-product
  of the ImageMagick solution and are not used by Magick.Native; the XML files are collected in step 3.
- `src\ImageMagick\Artifacts\fuzz\*.exe`: fuzzers, also unused by-products.
- `src\Magick.Native\bin\ReleaseQ16-HDRI\x64\`:

  | File | Size | Purpose |
  |---|---|---|
  | `Magick.Native-Q16-HDRI-x64.dll` | ~24 MB | The library Magick.NET loads. ImageMagick and all delegates are statically linked in. |
  | `Magick.Native-Q16-HDRI-x64.pdb` | ~125 MB | Debug symbols, needed to step into native code from .NET. |
  | `Magick.Native-Q16-HDRI-x64.lib` / `.exp` | small | Import library and exports file, only needed if another native project links against the DLL. |

The last line of the log is:

```
Magick.Native.vcxproj -> Z:\Magick.Native\src\Magick.Native\bin\ReleaseQ16-HDRI\x64\Magick.Native-Q16-HDRI-x64.dll
```

#### Pitfall: running the scripts from an environment with `NoDefaultCurrentDirectoryInExePath` set

The scripts call executables that live in the current directory by bare name (`Configure.Release.x64.exe`,
`vswhere.exe` inside `VsDevCmd.bat`, and `build.cmd` itself). If the environment variable
`NoDefaultCurrentDirectoryInExePath` is set, `cmd` refuses to look in the current directory and you get:

```
'Configure.Release.x64.exe' is not recognized as an internal or external command,
operable program or batch file.
```

A normal command prompt does not have this variable set. Some sandboxed or automated shells do. Clear it in that shell
before running the scripts:

```cmd
set NoDefaultCurrentDirectoryInExePath=
cd /d Z:\Magick.Native\build\windows
build.cmd Release Q16 x64 hdri noOpenMP
```

### Step 3: collect the outputs

These two scripts are what the GitHub workflow runs before uploading artifacts. They are optional locally, but they
gather exactly the files Magick.NET consumes.

```cmd
cd Z:\Magick.Native\build\windows
copy-native.cmd ..\..\artifacts ReleaseQ16-HDRI x64
copy-resources.cmd ..\..\resources-artifacts
```

- `copy-native.cmd <folder> <configuration> <architecture>` copies `src\Magick.Native\bin\<configuration>\<architecture>\*.dll`
  and `src\ImageMagick\Artifacts\NOTICE.txt` into `<folder>`.
- `copy-resources.cmd <folder>` copies the ImageMagick XML configuration files from `src\ImageMagick\Artifacts\bin\*.xml`
  and `src\Magick.Native\Resources\xml\*.xml` (`policy.xml`, `log.xml`) into `<folder>`. Magick.NET embeds these XML
  files into its assembly.

Result of running both with the arguments above:

```
Z:\Magick.Native\artifacts\
  Magick.Native-Q16-HDRI-x64.dll
  NOTICE.txt                       <- licenses of ImageMagick and every bundled delegate library

Z:\Magick.Native\resources-artifacts\
  colors.xml  configure.xml  delegates.xml  english.xml  locale.xml  log.xml  mime.xml
  policy.xml  thresholds.xml  type-ghostscript.xml  type.xml
```

`artifacts\` is covered by `.gitignore` (`**/artifacts/*`), but `resources-artifacts\` is not, so delete it or pick a
folder outside the repository if you do not want it to show up in `git status`.

### Rebuilding only Magick.Native

Once ImageMagick has been built by step 2, edits to the C sources in `src\Magick.Native` only need the second MSBuild
call. Either open `Magick.Native.sln` in Visual Studio and select the `ReleaseQ16-HDRI | x64` configuration, or from a
Developer Command Prompt for VS 2026:

```cmd
cd Z:\Magick.Native
msbuild Magick.Native.sln /p:Configuration=ReleaseQ16-HDRI,Platform=x64
```

Use a `DebugQ16-HDRI` configuration to step into the native code from a .NET debugger. A Debug configuration links
against the debug ImageMagick libraries, so step 2 must then have been run with `Debug` as its first argument.

## Linux: step by step on a plain Debian host

The GitHub workflow runs the Linux build inside an `ubuntu:20.04` container, and `.devcontainer/linux-x64` reproduces
that in Docker. The scripts themselves are plain bash and run just as well on a normal Linux machine. This section
describes that: a Debian host, no Docker, building the `Q16-HDRI` `x64` variant without OpenMP.

Everything installs under `/tmp` (`/tmp/dependencies`, `/tmp/ImageMagick`), so no sudo is needed after the build
tools are installed. Run every step as the same user: mixing sudo and non-sudo runs leaves root-owned folders under
`/tmp` that a later step cannot overwrite.

### Step 0: build tools

`build/linux-x64/install.build-tools.sh` targets Ubuntu 20.04 and fails on current Debian: it apt-installs `python`
(removed in Debian 12) and pip-installs cmake, which Debian blocks (externally managed environment). Install the
equivalent packages by hand instead:

```bash
sudo apt-get install -y autoconf automake autopoint binutils cmake curl gcc g++ git libtool locales make pkg-config unzip
```

Debian 12 ships cmake 3.25 and Debian 13 ships 3.31; `src/Magick.Native/CMakeLists.txt` accepts anything from 2.8 up.

### Step 1: check out ImageMagick and download the prebuilt dependencies

```bash
cd src/ImageMagick
./checkout.sh --no-configure --dependencies-artifact linux-x64-static.zip
```

- Clones `https://github.com/ImageMagick/ImageMagick.git` into `src/ImageMagick/ImageMagick` and checks out the commit
  from `ImageMagick.commit` (detached HEAD is expected).
- `--no-configure` skips downloading the Windows-only Configure tool.
- `--dependencies-artifact linux-x64-static.zip` downloads the prebuilt static delegate libraries (libpng, libjpeg-turbo,
  libheif, libjxl, freetype, pango, cairo, ...) from the ImageMagick repository and, on Linux, moves the extracted
  `Artifacts` folder to `/tmp/dependencies`.

Verify:

```bash
ls src/ImageMagick/ImageMagick/configure.ac   # source is there
ls /tmp/dependencies/lib | head               # about 40 .a files
ls /tmp/dependencies/include | head
```

### Step 2: build ImageMagick

```bash
cd src/ImageMagick/ImageMagick
../../../build/shared/build.imagemagick.sh linux x64 Q16-HDRI noOpenMP
```

Arguments: platform (`linux`, `linux-musl`, `macos`, `wasm`), architecture, quantum (`Q8`, `Q16`, `Q16-HDRI`), and
literally `OpenMP` to enable OpenMP or anything else to disable it. The script:

1. Sources `build/linux-x64/settings.sh` (`-O3 -fPIC -Wall -DNDEBUG`; set `DEBUG_BUILD=yes` in the environment for
   `-g3 -O0` and a CMake Debug build).
2. Runs `autoreconf -fiv`.
3. Runs `./configure --disable-shared --enable-static --with-quantum-depth=16 --enable-hdri=yes --disable-openmp ...`
   with `--prefix=/tmp/ImageMagick`.
4. Runs `make -j$(nproc) install`.
5. Copies ImageMagick's `*-private.h` headers into `/tmp/ImageMagick/include/ImageMagick-7`, because the shim includes
   them (see `Stdafx.h`).

This is the slow step (10 to 30 minutes depending on the machine). Verify:

```bash
ls /tmp/ImageMagick/lib/libMagickCore-7.Q16HDRI.a /tmp/ImageMagick/lib/libMagickWand-7.Q16HDRI.a
ls /tmp/ImageMagick/include/ImageMagick-7/MagickCore/string-private.h
```

Note the quantum name inside the library file name has no dash: `Q16HDRI`.

### Step 3: build Magick.Native

```bash
cd src/Magick.Native
../../build/shared/build.native.sh linux x64 Q16-HDRI noOpenMP
```

Creates `src/Magick.Native/Q16-HDRI/` (deleted and recreated on every run), runs cmake there with
`-DDEPTH=16 -DHDRI_ENABLE=1 -DOPENMP=0 -DQUANTUM_NAME=Q16HDRI -DPLATFORM=LINUX ...`, then `make`. `CMakeLists.txt`
hard-codes `/tmp/ImageMagick` and `/tmp/dependencies`, which is why the previous steps had to land there. Takes a
minute or two. Output:

```
src/Magick.Native/Q16-HDRI/libMagick.Native-Q16-HDRI-x64.dll.so
```

### Step 4: copy and verify

```bash
cd src/Magick.Native
../../build/shared/copy.native.sh ../../artifacts linux x64 Q16-HDRI noOpenMP
ldd ../../artifacts/Magick.Native-Q16-HDRI-x64.dll.so
nm -D ../../artifacts/Magick.Native-Q16-HDRI-x64.dll.so | grep ' T MagickImage_Blur'
```

`copy.native.sh` strips the `lib` prefix so the file gets the `Magick.Native-Q16-HDRI-x64.dll.so` name Magick.NET
expects (the `.dll` is kept on every platform). `ldd` should list only system libraries (`libc`, `libm`, `libpthread`,
`libdl`, `libresolv`) with no "not found" and, for a non-OpenMP build, no `libgomp`. The `nm` line confirms the shim's
exports are visible. `build/shared/verify.native.sh` is the CI version of these checks.

### Portability of the result

The `.so` depends on the glibc of the machine that built it. CI builds on Ubuntu 20.04 so the released binaries load on
old distributions. A binary built on a current Debian host runs on hosts with the same or newer glibc, but not on
anything older. For musl-based systems (Alpine) use the `linux-musl` platform and `build/linux-musl-x64`.

### Using the local build from Magick.NET

Magick.NET normally downloads a released Magick.Native and copies the DLL into every test project's output folder
(`tests\<Project>\bin\TestQ16-HDRI\x64\<tfm>\`). To test a locally built DLL instead, copy
`src\Magick.Native\bin\ReleaseQ16-HDRI\x64\Magick.Native-Q16-HDRI-x64.dll` over the DLL in those folders, and copy the
XML files from step 3 into `<Magick.NET>\src\Magick.Native\resources\ReleaseQ16-HDRI\x64\`.
